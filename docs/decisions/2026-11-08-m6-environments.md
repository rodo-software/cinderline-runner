# M6 environments: where services are defined, and how `existing` gets tools, clone and secrets

- **Status:** Accepted
- **Date:** 2026-11-08, point 5 added 2026-11-10
- **Source:** Decided by Willem on CSR-51, settling the open items of plan M6 that decision 2026-11-05-runner-rewrite-details point 18 kept open. Points 1 to 4 on 2026-11-08, each the option proposed by Claude (point 1 after a second round). Point 5 on 2026-11-10, option A of two proposed by Claude, because point 2 clashed with decision 2026-11-09-network-allowlist; it amends point 2.

## Decision

1. **Services of a per-project image (`docker`):** a dedicated compose file in the repository, read from the base branch only. Its path is set per project in Cinderline by an admin (default `.cinderline/compose.yml`), with the name of the agent service (default `agent`). The file declares the services (a database, Redis, others) and the agent service, whose image is pulled or built. Per issue, the runner runs it under its own compose project name. It adds the tools, clone and state mounts and the turn's environment itself, and removes everything with `down -v` after the run. Before starting, it reads the normalised config (`docker compose config --format json`) and refuses bind mounts, `privileged`, host network or PID namespace, `cap_add`, devices and published ports, with an error reported to Cinderline. The compose project's network is internal, with the run's egress proxy as its only way out (decision 2026-11-09-network-allowlist). The default environment becomes a built-in compose file of the same shape: the default image plus MySQL. `docker compose` becomes a prerequisite.
2. **`existing`: how the tools get in:** a sidecar. The runner starts its own agent container from the image of the named service in the developer's Docker Compose or Lando setup, on the run's internal network (point 5). It mounts the tools volume, the clone and the state volume as the `docker` kind does, and removes the container after the turn. The developer's containers are never restarted, recreated or copied into.
3. **`existing`: where the clone lives:** in the runner's `runs` volume, as for the `docker` kind, mounted into the sidecar. Never the developer's working tree. This follows from point 2.
4. **`existing`: which secrets may enter:** the same rule as every kind. The sidecar gets the turn's model credential, its scoped token and the client's settings, plus non-secret `KEY=value` pairs listed in the project's local configuration next to the `existing` allowance (for example `DB_HOST=database`). Nothing is copied from the developer's running containers. The sidecar can reach the developer services attached to its network (point 5), including their database and its data. Allowing `existing` in local configuration (0098) is the developer's consent to that. The README and the warning `add` prints when `existing` is allowed say so.
5. **`existing`: network:** the sidecar sits only on the run's internal network, with the egress proxy as its only way out, as for every kind. For the run, the runner attaches the developer services listed in the project's local configuration (for example `database`) to that network with `docker network connect`, under their service name, and detaches them afterwards; recovery at start detaches them after a crash. The developer's containers gain a network for the length of the run and are not restarted or recreated.

## Reason

1. Compose is the standard that Lando, DDEV and Docker Desktop all produce, and it lets developers define their own environment with healthchecks, volumes and commands. A `.lando.yml` would need Lando installed and allows one app per directory, so no parallel issues. A developer's own compose file bind-mounts their working tree and publishes ports, and stripping those with an override is fragile. A services list in Cinderline would be a second, non-standard format. Reading from the base branch means a pull request cannot change what runs for its own issue. One mechanism for the default and per-project images keeps one `Environment` implementation.
2. A running container's mounts are fixed. Copying about 320 MB of tools into each developer container is lost on every Lando rebuild. Recreating the developer's service restarts their app mid-work. A sidecar reuses the `docker` kind's mounts and allows parallel issues.
3. Same reason as 2: the `runs` volume is already how agent containers see their clone (M4).
4. Copying the developer's container environment would send every key they injected into their dev setup to the agent and the model provider. That breaks the rule that only the one model credential and its scoped token enter a container. One rule for every kind is checkable in one place.
5. The developer's Compose or Lando network is an ordinary bridge with a route out. A sidecar on it would bypass the allowlist entirely, so an injected issue body could send the clone or the scoped token anywhere, from the setup most likely to hold real data. Attaching only the listed services keeps one network rule for every kind. Rejected: exempting `existing` from the allowlist, and putting the sidecar on both networks (the developer's network still gives it a route out).
