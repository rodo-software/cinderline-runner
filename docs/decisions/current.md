# Cinderline runner: decisions in force

What is true for the runner now, as of 2026-11-26. This file replaces the records in [archive/](archive/), which are history and not binding: where a rule here and an archived record differ, this file wins. The few dated records next to this file are in force too; see [README.md](README.md).

A new decision gets its own dated record next to this file, `YYYY-MM-DD-topic.md`, and is folded in here and archived once it is built (see [README.md](README.md)). Each rule ends with its sources: record names (in archive/ unless they sit next to this file), or Willem's answers of 2026-11-17. Decisions of the app repository are cited by their name there.

## What the runner is and is not

- The runner does the mechanics and reports facts; the app decides every step and writes every text a person reads on an issue. The runner never reads or writes an issue. (2026-11-16-runner-protocol-v2)
- What stays in the runner: containers, git, the forge calls, the agent CLIs, sessions and their notes, the limits for expiring sessions, verifying a resolved merge, the repository pin, and what may enter a container. (2026-11-16-runner-protocol-v2)
- The app writes every prompt: the agent's own instructions first, then the rules, then the issue text last, marked as data. The runner passes it on unchanged. (2026-11-06-prompts; 2026-11-16-runner-protocol-v2)
- Issues are the only workflow state (app decision 0091). The runner keeps only caches it may lose: session notes, the outbox, clones. (2026-11-05-runner-state-location; 2026-11-16-runner-protocol-v2)
- There are no writer teams and no writer run. (2026-11-06-no-writer-teams)
- The runner serves a web page on the user's own machine (2026-11-26-local-web-page); runners are shown read-only in the hosted app. Controlling a runner from the app needs Willem's decision first, because it would move secrets through the server. (2026-11-11-runners-in-the-app)
- The local web page only watches runs: no control stops, retries or skips a single run, because that is the app's policy. Nothing about the page goes to the app: no poll field, no contract change. (2026-11-26-local-web-page)
- The runner runs no model itself: no model backends, no downloads, no GPU work. Running models is the customer's own matter. (2026-11-11-no-local-model-work; 2026-11-17-local-model-providers)

Reason: no competitor may profit, while Cinderline's users may run it. The app stays closed source. (2026-11-16-fsl-licence; Willem 2026-11-17, answer 10)

- Agents never edit `.forgejo/` or `.github/`, and never commit secrets, tokens or `.env` files. The old Node runner in `legacy/` is deleted and no longer ignored; text that cites it as history stays. (2026-11-05-forgejo-daily-github-public; 2026-11-26-legacy-deleted)
- Releases and the default image carry build provenance attestations, because the GitHub repository is public; the attest steps skip themselves on a private repository. The installers check SHA-256 against `checksums.txt` either way. (2026-11-16-attest-when-public; 2026-11-05-runner-rewrite-details; Willem 2026-11-17, answer 19)
- The module and the GHCR images are `github.com/rodo-software/cinderline-runner`. (2026-11-05-runner-rewrite-details)

When that folder is not on PATH, `install.sh` adds the export to the shell's profile (not for fish and other syntaxes) and `install.ps1` to the user PATH; `CINDERLINE_NO_MODIFY_PATH=1` opts out. `cinderline update` runs the install script. (2026-11-05-runner-rewrite-details; 2026-11-11-install-path; 2026-11-11-audit-fixes)
- On a `426` the project takes no new work, logs once at Error, shows "cinderline needs runner ≥ X; run `cinderline update` and then `cinderline run`" in `status`, and polls again only after an hour. Auto-update is not built; it would be opt-in. (2026-11-16-upgrade-required)

## Language, dependencies and code rules

- Go's standard library first; every dependency needs a one-line reason in a record. The allowed ones:
  - `github.com/zalando/go-keyring`: the OS keychain on three systems without cgo. (2026-11-05-go-keyring)
  - `github.com/kardianos/service`: the LaunchAgent and the systemd user unit. (2026-11-07-kardianos-service)
  - `golang.org/x/term`: hidden input in `key set`; the Go team's, adding only `x/sys`. (2026-11-16-x-term)
  - `go.yaml.in/yaml/v3`: parses a compose file's YAML, with aliases and merge keys, for the compose preflight; Go's standard library has no YAML parser. (2026-11-19-compose-local-files)
- The name `cinderline` (command, config folder, service, keychain, branch prefix, MCP server name, version header) lives in one constant. (2026-11-05-runner-rewrite-details)
- The runner shells out to the `docker` command, never the Docker SDK. The only interfaces are `Client`, `Forge`, `Environment` and `Workspace`. (AGENTS.md)
- The web page is plain HTML, CSS and JavaScript in `internal/web/static/`, embedded with `go:embed`, with live data over server-sent events. No npm, bundler, framework or new Go dependency. (2026-11-26-local-web-page)
- Every change to the config or the secrets goes through `internal/manage`, which the CLI commands and the page's handlers both call, with no new interface; the CLI keeps working with the daemon stopped. (2026-11-26-local-web-page)

## The runner API

- The contract is [2026-11-16-runner-protocol-v2](2026-11-16-runner-protocol-v2.md), next to this file, with [`docs/runner-api/openapi.yaml`](../runner-api/openapi.yaml). Read them there; this file does not copy them. Its amendments (2026-11-17-second-audit-decisions, 2026-11-17-local-model-providers and later) are the rules below.
- Three requests under `/api/runner/v2`: the poll, `runs/{ref}/next`, and the attachment download. A step never carries a command, a path, a docker option, an environment variable or a URL. (2026-11-16-runner-protocol-v2)
- The OpenAPI file is authored in the app repository and copied here; a contract change starts there. (AGENTS.md; 2026-11-16-runner-protocol-v2)
- `contractSHA256` in `internal/cinderline` pins the SHA-256 of the copied file, and a test fails when they differ: a copy updates the constant and the types in the same commit. Whether the copy is behind the app is seen only by comparing `sha256sum` of the app's file with the constant; CI cannot, as the app repository is private. Until the app's file gets a version line of its own (a CL issue), the hash is the only marker. (2026-11-26-contract-hash)
- A project's Cinderline URL must be `https`; plain `http` only when the host is `localhost` or a loopback address (`127.0.0.0/8`, `::1`), not `host.docker.internal` or a private address. `add` refuses another URL before it sends the runner token; a `config.json` that holds one fails to load (the daemon does not start, a reload keeps the old config, every command reports it). No warn-only path. (2026-11-19-https-instance)
- A stop during publishing still pushes and opens the pull request but does not ask the forge to merge: `merge: null`. A stop while waiting for a merge already asked for reports `merge: pending`. (2026-11-17-second-audit-decisions)
- There is no `X-Cinderline-Agent` header; an MCP request's agent name is its token's name. (2026-11-17-second-audit-decisions)

## The loop, runs, sessions and tidying

- One loop per project and at most `max_parallel_runs` team runs at once: the project's own, else the runner-wide one at the top of `config.json`, else 1, each 1 to 10, set with `cinderline parallel`, each in its own slot, clone and branch, plus at most one Project Manager run next to them in its own slot: the poll always sends `manager_idle` and starts `manager_job`; with more than one team slot it sends `max_parallel` and starts `jobs`, one per free slot. An answer with only `job`, from an app before lanes, starts only while no team run is in flight. (app decision 2026-11-24-lanes; 2026-11-24-housekeeping-next-to-runs; 2026-11-25-parallel-runs-default)
- The Review upkeep pass and tidying run next to the runs and never touch an issue in flight; a job for an issue of the pass in flight waits; tidying is done in the poll before the pass it starts and never overlaps a pass. A poll that asks for the Review list also offers its free slots. The workspace locks the bare repository for every fetch and push. (2026-11-24-housekeeping-next-to-runs)
- A manager run gets only `run` and `stop` steps, works in a fresh clone of the base removed at its end, and never commits or pushes, not at `stop` either (`not_pushed`); tidying never pushes its clone. (2026-11-16-runner-protocol-v2; app decision 2026-11-17-project-manager; CLR-194)
- A slot is offered (`idle`, `manager_idle`) only while its run fits in the runner's one memory budget, which all projects share: Docker's `MemTotal` less 1 GiB. A run counts its agent container's limit plus each other compose service's `mem_limit`, or 512 MiB without one. The slot reserves that memory when it sends the poll, frees it when the answer brings no job, and its run holds it until it ends; a run larger than the whole budget runs alone, with a warning. Waiting for memory is not reported to the app. (2026-11-24-agent-memory-limit; CLR-216)
- The budget is read at the first slot that would be offered, again until Docker answers (no slot is offered until then), and kept until the runner restarts. Until a run of the project has read its compose file, the run's size is the agent's limit alone. A run whose start finds another size takes it, and drops its job before its first `next` when that no longer fits. A project's two free slots take turns when only one fits. A slot logs once when it starts to wait; `status` shows the budget, the reservations, each run's size and the projects that wait. On macOS only the Docker VM's size is seen. (2026-11-24-agent-memory-limit)
- A run that does not start leaves the issue in To do; the loop then waits 1 minute, doubling to 10. (2026-11-07-publish-resilience)
- A session resumes only when its clone still exists in the runs volume (2026-11-11-audit-fixes), except a Project Manager's, which resumes in a fresh clone at the same dir (CLR-194).
- A reload (`POST /reload`) re-reads `config.json`; a config that fails to load keeps the old one, and the caller gets the error. Each project loop then drains on its own and starts again with the newest config once nothing is in flight (no issue run, Project Manager run or upkeep pass); a project the config adds starts at once, a removed one drains and ends, and a loop for an ID starts only once the old loop with that ID has ended. No run is cut and the process does not exit. (2026-11-05-reload-config; 2026-11-24-rolling-reload)
- The team's `max_turns` is passed to every agent turn; the app always sends a number. (2026-11-07-team-max-turns)
- The idle limit is the project's `idle_minutes`, for every agent turn. Claude Code runs with `--output-format stream-json --verbose`, so one idle timer on the output stream serves every client. (2026-11-14-run-failsafes)
- The check runs the project's `check_command` through `sh -c` in the clone, after committing and pushing, in the agent's environment without credentials, client state or tools, with the team's `max_minutes` as limit. Fixes, verdicts and what follows a failure are the app's. (2026-11-16-check-step)
- A turn's or a check's output keeps its first 1 MB and last 128 MB; past that the middle is replaced by one line `[N bytes of output cut]` and a warning is logged. The session ID, report, final usage and limits are still read; tool counts and OpenCode's tokens and cost miss a cut middle. A line still unfinished after 1 MB is not logged, one placeholder line stands for it. (2026-11-24-output-cap)
- The runner verifies a resolved merge (clean tree, base and old head are ancestors, no conflict markers, no "Blocked" report) and undoes one it cannot verify. (2026-11-07-solo-team-resolves-merge-conflicts)
- Tidying pushes stranded clones (commits no remote branch has), never forced; a failure only logs. (2026-11-07-publish-resilience; 2026-11-11-audit-fixes)
- Each run is kept on disk for the page, `transcripts/<project>/<issue>/<run>/<NN>-<kind>.ndjson` in the state folder, one file per step, one JSON object per line: a cache the runner may lose, never a run table; a write error only logs. `transcript_days` (0 to 365, default 14, runner-wide or a project's own, which wins) is how long a run is kept; 0 removes a run when it ends. `transcript_max_size` (runner-wide, at least 100m, default 1g, written like `memory`) caps them all, oldest removed first. Old runs are removed at start and hourly. (2026-11-26-local-web-page)
- The page shows a run as its steps in order with their outcomes and refused hosts, and an agent turn as its prompt (folded) and a timeline parsed from the client's output (Claude Code and Codex); other clients and unknown lines show as raw lines, which are always one click away. Project Manager runs are shown like team runs, marked as such. The live CPU and memory of the agent container and each compose service (not the proxy) come from `docker stats` only while a page watches that run, and are kept in memory only. (2026-11-26-local-web-page)

## Git, workspaces and branches

- Each issue gets its own clone in a runs volume, sharing objects through alternates. The git token stays in a helper container, which never runs git in the agent's clone. (2026-11-05-runner-rewrite-details)
- An agent's or check's container mounts only its issue's folder of the runs volume, at `/runs/<REF>`, with the repo volume read-only; the runner's own git containers mount the whole volume. (2026-11-19-docker-26)
- Pushes are never forced. (2026-11-07-publish-resilience)
- Review upkeep is git only, no agent: one fetch per pass finds the branches that are behind; a stranded clone is pushed before it is replaced, and nothing is replaced when the list fails. (2026-11-07-solo-team-resolves-merge-conflicts; 2026-11-11-audit-fixes)
- A configured project is its Cinderline URL, workspace slug and key. Docker objects, keychain entries and state files are named by its `id`, set at `add` to `<workspace>-<KEY>`, or the key alone in workspace `default`; an entry without one gets that name from its key when it is loaded. `add` refuses a duplicate, and the daemon runs only the first of two with one ID. (2026-11-15-workspace-in-project-identity; 2026-11-17-project-key-rename)
- After a key rename in the app, `rename --project OLD [-url URL] [-workspace SLUG]` takes the new key from the instance and gives the entry the `id` of that key: settings stay, secrets move (written under the new `id` first, the old removed after the config is saved), and the old Docker volumes, session notes and sign-ins are removed. It refuses while the project runs an issue, has a paused run or has undelivered reports, and when another project already has the new `id`. The runner never changes a key or an `id` by itself. (2026-11-17-rename-moves-local-names)
- Fields an older runner wrote in `config.json` are ignored with a warning; any other unknown field is refused. (2026-11-17-project-key-rename)
- Project links are one way and never chain. A's agents may read and edit B's issues over MCP and read B's repositories read-only; every change stays in A's repository. The runner fetches B's code only when B is added on this runner in the same workspace; otherwise the run goes on without it. (2026-11-11-project-links; 2026-11-15-workspace-in-project-identity)

## Forges and pull requests

- Publish (base merge, push, pull request) is tried 5 times, waiting 30 seconds and doubling. (2026-11-07-publish-resilience)
- Forgejo finds a branch's pull request by `head.label`, walking the list, never `pulls/{base}/{head}`. (2026-11-07-publish-resilience)
- Every failed check the runner sends has a `log`: the end of the CI log, its read tried once more; without one, a line saying why, then the forge's own text (GitHub's check output, else the check's description), else a line that the forge says only that it failed. (2026-11-25-ci-log-always)
- The runner reads every failure the forge reports: GitHub's commit statuses and check runs (10 pages of 100 at most), GitLab's external commit statuses, Bitbucket's build statuses (10 pages at most) and the log of a Bitbucket Pipelines build's first failed step. A failed state without a failed check becomes one check with the forge's words; never `failed` without a check. No text of a check carries a URL (`<URL>` instead); `url` keeps its own field. (2026-11-25-ci-log-always)

## Environments, containers and the default image

- There are two environments: `default` and `docker`. The `existing` environment is dropped. (Willem 2026-11-17, answer 5)
- Every agent turn runs in its own `docker run --rm` container on its own internal network, stopped with `docker stop` at the team's `max_minutes`, so no process outlives a turn. `Environment` is `Run` plus `Cleanup`. (2026-11-06-container-per-turn)
- The default environment is the default image behind the egress proxy, with no other service and no database; a project that needs MySQL brings it in its compose file, as the README shows for Laravel. (2026-11-11-docker-compose-environment; 2026-11-26-no-database-in-default-image)
- A `docker` project's services come from a compose file in its repository, read from the base branch only (default `.cinderline/compose.yml`, agent service `agent`, both set in Cinderline), run on the run's internal network behind the proxy and removed with `down -v`. (2026-11-08-m6-environments)
- The base branch's tree is copied without symlinks; `docker compose config --format json` is checked against an allowlist of keys; an override puts every service on the run's network. Compose gets only the variables the docker CLI needs. Recovery removes labelled compose volumes. (2026-11-11-docker-compose-environment)
- Repository-local `include` and external-file `extends` are kept: before Compose reads anything, their file references (also an include's `env_file` and `project_directory`) are validated recursively, and a path outside the copied repository or a dynamic reference that cannot be validated first is refused. The composition is then resolved without interpolation into a temporary JSON file in the copy, which every later check and operation uses, with an explicit root `.env` (an empty one when absent); service `env_file` paths are checked before their values are read. (2026-11-19-compose-local-files)
- The agent runs with `docker run` in the agent service's image, hardened as in the default environment, never with that service's command, entrypoint, user or mounts. (2026-11-11-docker-compose-environment)
- Every agent and check container runs with `--memory` equal to `--memory-swap`, so without swap: 4 GiB by default, the project's `memory` in `config.json` (whole MiB `m` or GiB `g`, 1024-based, at least `256m`, set with `cinderline memory show|set SIZE|clear --project KEY`) instead, and a `mem_limit` on the compose file's agent service over both, as a byte count in a string or a plain number. The egress proxy gets a fixed 64 MiB; a compose file's other services get no default; `cpus` and `pids_limit` on the agent service stay unused. (2026-11-24-agent-memory-limit)
- A project that needs another toolchain uses `docker`: a Dockerfile and `.cinderline/compose.yml` in its repository. An agent image needs `/bin/sh` and a glibc or musl loader and runs as uid 1000; agent CLIs come from the tools volume. (2026-11-16-project-toolchains)
- The default image holds PHP 8.4 (with bcmath, gd, intl, pdo_mysql and zip, and `memory_limit = -1` for the CLI, as setup-php runs it), Composer, Node 22, git, procps and Debian's headless Chromium (CLR-319: run with `--no-sandbox`, which the hardened container refuses anyway, with the Google service hosts it asks for by itself in its own `no_proxy` so the proxy sees none of them (CLR-320), and pointed at by `CHROME_PATH` and the Puppeteer and Playwright variables, so agents download no browser); Go left it once the runner project had its own image. gd, procps and the memory limit are in the image for every project rather than in a project's compose file, because their absence failed a PHPUnit suite that CI passed (CLKP-3). (2026-11-16-project-toolchains point 3; CLR-185; Willem, CLR-264)
- The default image is built only when `images/default/` changes on main (or by hand), natively for linux/arm64 and linux/amd64, each pushed by digest and merged into one manifest list tagged with the Dockerfile's sum; the attestation and the pin are that list's digest, and only a list with both platforms is pinned (a test fails when the pin matches while the workflow lacks linux/amd64). The workflow is drafted in `docs/ci/default-image.yml`. A failed pull of the pinned image is an error; the runner builds locally only a Dockerfile with no pin yet. (2026-11-12-ci-speedups; 2026-11-24-default-image-amd64)
- `add` and `service install` fail at once without docker, a running daemon or 5 GB free; `run` fails at once on missing docker or low disk but waits for the daemon, retrying every 10 seconds, because the service starts before Docker Desktop answers. Docker Engine must be 26.0+ (Docker Desktop 4.29+), for `volume-subpath` and the fix for CVE-2024-29018; `add`, `service install` and `run` refuse an older one. (2026-11-08-docker-prereq; 2026-11-11-audit-fixes; 2026-11-19-docker-26)

## Network and the proxy

- Agents reach only exact `host:port` pairs through the run's egress proxy: their own client's provider (plus its sign-in hosts on a stored login), the project's Cinderline host, the listed package registries on 443, and the project's `allow_hosts`. Never a forge. Only local config opens a host for every run. (2026-11-09-network-allowlist; 2026-11-17-hosts-from-cinderline)
- A person's *Yes, this run* in Cinderline opens a refused host for one issue's runs: its `run`, `resolve` and `check` steps carry `allow_hosts`, each checked as a local `allow_hosts` entry and additionally refusing private, link-local unicast and unspecified IP literals, an invalid one dropped with a log line while the step goes on. The proxy also refuses private, loopback, link-local unicast and unspecified resolved addresses for app approvals, for HTTP and CONNECT; local config retains private-network access and takes precedence for the same host and port. Strict host blocking (`strict_hosts`, runner-wide, off by default, set with `cinderline strict-hosts on|off`, reported in every poll) ignores app approvals. Each of those steps reports the hosts the proxy refused during it as `last.refused`: at most 20, one per `host:port`, each with its reason (`not_allowed`, `private_address`, `strict`, `runner_machine`) and the first request's method and URL without query, fragment or user info when the proxy read it. For that the proxy ends the TLS of a refused HTTPS host with a certificate from the turn's intermediate of the runner's CA, reads only the first request and answers `403`; it never decrypts an allowed host or the runner's own machine. (2026-11-17-hosts-from-cinderline; 2026-11-19-app-host-addresses; app decision 2026-11-25-blocked-host-urls)
- Only a well-formed `host:port` of at most 260 characters is reported as refused, and none that holds a secret the runner knows: such a host is left out, a method and URL that hold one are dropped, never redacted or clipped. `refused_connections` in the report counts every refused connection. (2026-11-17-hosts-from-cinderline; app decision 2026-11-25-blocked-host-urls)
- An agent CLI's own background traffic (model catalogs, update checks, plugin syncs, tool downloads) is switched off by a flag, config key or variable, or bundled in the tools volume, where the version allows. Only when it cannot be and the client needs it to work is its host added to that client's own `hosts` in `internal/client/<client>.go`, with a comment naming the version it was checked with and how. A later version that needs another host shows up as a refused host. Never through `Registries` or `allow_hosts`, which are for the project's own work. (2026-11-25-client-own-traffic)
- A job's skill packages (`skills`) are each checked before any field is used, refused on a strict runner unless an `allow_skills` entry allows its name and URL (`cinderline allow-skill`), and fetched on the runner's own network without a token at the commit the app resolved, any other refused, into one read-only volume per URL and commit that every project shares. Each one named is reported in `workspace.skills` as `loaded`, `refused_strict` or `failed`; a volume no run used for 30 days is tidied. (2026-11-26-skill-package-fetch; app decision 2026-11-26-skill-packages)
- A package's `name` is lower-case letters and digits with single hyphens, at most 64; its `url` https without user info, query or fragment, at most 500; its `commit` 40 lower-case hex; its `path` relative, clean, without `..`, at most 200, of letters, digits and `. _ @ + - /`, a folder of the repository reached without a symlink. A failing entry is `failed` and the run goes on; only the first 10 are used, and a repeated name is `failed`. The fetch is `git fetch --depth 1` in a throwaway git container in the run's prepare, refused when `HEAD` is not the commit, `.git` removed, with git's credential prompt off: private repositories are out of scope. (2026-11-26-skill-package-fetch)
- A package volume (`cinderline-skill-<hash>`, the repository in `repo/`, a `complete` marker at the root written last) is filled once behind a file lock in the state folder; the lock file's time is its last use, and lock files are never removed. `uninstall` removes the volumes with the tools volumes. `allow-skill add NAME URL|list|remove NAME [--project KEY]` writes `allow_skills`, runner-wide (after a confirmation) or per project, one URL per name, the URL exactly the catalog's. (2026-11-26-skill-package-fetch)
- A package's `downloads` (at most 10 of `{arch, path, url, sha256, executable}`, declared in the catalog) are checked with the package: `arch` `amd64` or `arm64`, `path` and `url` with the package's rules, `sha256` 64 lower-case hex. When its volume is filled, the runner fetches those of its engine's arch over its own network, each capped at 200 MB and 10 minutes, and refuses any that doesn't match its hash. It writes them into the package's root (755 or 644), never through a symlink, before the `complete` marker. With downloads, the root and the downloads name the volume too. A failed download fails the package. A strict runner refuses a package with downloads (`refused_strict`): `allow_skills` names the package's URL only. (2026-11-28-skill-downloads)
- Every turn of a run, not the check, mounts each loaded package's repository read-only at `/skills/<name>` and loads it per client: Claude Code one `--plugin-dir` per package with `--strict-mcp-config` kept, never `--bare`; Gemini CLI an extension for a package with `gemini-extension.json`, else one mount per skill folder, a later package's clashing skill name left out and logged; OpenCode `skills.paths` and the package's `.opencode/{plugin,plugins}/*.{ts,js}`; Codex its `skills/` only. The client folders that get mounts are a tmpfs per turn. Only names the runner's own volume check listed (letters, digits, `. _ -`, no leading dot, no symlink) become mounts. Nothing is written into the clone and nothing is added to the allowlist; hooks need their interpreter in the image. The ponytail pin is gone. (2026-11-26-skill-package-mounts)
- `host.docker.internal` is reachable only on the port of a model provider on the runner's own machine, for a turn that uses it, through the proxy only; a runner provider elsewhere is allowed on exactly its host and port, for such a turn only. `allow_hosts` refuses `localhost`, loopback addresses and `host.docker.internal`. (2026-11-17-local-model-providers; Willem 2026-11-17, extras)
- Agent containers never reach the web page's port: the proxy refuses the runner's own machine, an app approval of it is dropped, and the config refuses a provider on the runner's own machine on the page's port, whether the page is on or not. (2026-11-26-local-web-page)

## Secrets and redaction

- Secrets are in the OS keychain; when the keychain fails, a 0600 file in the state folder. (2026-11-05-go-keyring)
- No secret enters an agent container except the one model credential the turn needs and its scoped token. (AGENTS.md)
- Every secret the runner holds (runner token, git tokens, model and provider keys, scoped agent tokens) is replaced by a marker in log lines, in everything sent to the app, and in pull request titles and bodies, also base64, hex and URL-encoded. Values under 16 characters are skipped. It is a second line of defence only. (2026-11-11-secret-redaction; 2026-11-17-local-model-providers)
- The runner never reads the sign-in files on the state volumes. (2026-11-11-secret-redaction)
- Every push is scanned first: a value the runner holds, in any redacted form, in the header, message or added lines of a commit no other remote branch has stops the push and keeps the clone; a well-known shape of secret only warns. `publish` and `stop` report it with the outcome `secret` and the list `secrets` (kind, commit, path, never the value); the agent rewrites its unpushed commits. (2026-11-17-open-questions-answered, point 2; [2026-11-17-push-scan](2026-11-17-push-scan.md))
- The web page's token is 32 random bytes in `web-token` in the state folder (0600), made when first needed, replaced by `web --new-token` and read on every request. `GET /?token=…` with it sets a cookie (HttpOnly, SameSite=Strict) and redirects to `/`; every other request needs the cookie, else `401` with a line naming `cinderline web`. The `Host` must be `127.0.0.1:<port>` or `localhost:<port>`, else `403` (DNS rebinding); a request other than GET or HEAD needs the page's own `Origin` or `Sec-Fetch-Site: same-origin`, else `403`. (2026-11-26-local-web-page)
- Secrets are write-only on the page: it sets and deletes them and shows whether each is set, never a value, in no answer and no error. (2026-11-26-local-web-page)
- Every transcript line passes `internal/redact` before it is stored or sent to the page; there is no way to see an unredacted line. (2026-11-26-local-web-page)

## Agent clients and the tools volume

- Detection per client: `missing_binary` when `--version` fails; `missing_credential` with neither key nor login file (checked for existence only); `invalid_credential` only on HTTP 401 or 403 from one free provider call; else `ready`. Logins, setup-tokens and Vertex keys are never tested. Detection runs at start and every hour. (2026-11-09-client-detection)
- Client sessions and config live on one Docker state volume per client and project; the host state folder holds the log, session notes, the outbox and attachments. Both are caches. (2026-11-05-runner-state-location; 2026-11-11-audit-fixes)
- A turn without a scoped token runs without the project's `CLAUDE.md`, `AGENTS.md` and OpenCode config. (2026-11-06-m3-parity-gaps)
- The agent CLIs follow their vendors' latest releases, checked by the hashes each vendor publishes: Claude Code's `stable` channel and its `manifest.json`, npm `latest` and `dist.integrity` for OpenCode and Gemini CLI, Codex's latest GitHub release `rust-v*` and its assets' digests. The runner resolves them 5 minutes after start and then hourly. A new set goes live for the runs that start after it, once each running project's check passed: `--version` prints a version, and a client whose live CLI listed models lists some. A client that fails keeps its version, with a warning in the log. A run keeps the tools mount of its prepare. The live and previous versions are in `tools/versions.json` in the state folder, pins.go's without it. Other tools volumes go once unmounted for 24 hours. `cinderline pin CLIENT VERSION|latest` (`pinned` in config.json) holds one CLI at a version. Node and ripgrep stay pinned. ([2026-11-27-agent-cli-updates](2026-11-27-agent-cli-updates.md))
- The tools volume carries Gemini CLI's npm tarball (checked by sha512) and Node 22: from nodejs.org checked by SHA-256 on glibc, from the digest-pinned `node:22-alpine` on musl, so Gemini runs on any agent image. (2026-11-08-gemini-node-in-tools-volume)
- Model keys are per project; `add` asks for the four, each optional, and offers to copy them from another project. A stored key wins over a login; a successful `login` deletes the client's stored key (one that fails or leaves no credentials file keeps it), a later `key set` wins again. No key is printed back. (2026-11-05-runner-rewrite-details; 2026-11-10-model-keys; 2026-11-19-login-replaces-key)
- A resumed Codex session's usage is the session's total so far, so the runner keeps each held session's last total next to its ID (in the lead's session note across runs) and reports a turn's usage as the difference, each count at least 0; a new session starts at zero. The contract stays per turn. (2026-11-24-codex-usage-difference)

## Model providers

- A provider is added once on the runner, for all its projects: a name (lower-case letters, digits and dashes; not `openrouter`), an OpenAI-compatible base URL (`http` or `https`), and an optional key kept with the other secrets. A project uses one by naming it in an agent's model; there is no switch per project. (2026-11-17-local-model-providers)
- An OpenCode agent's model is `<provider>/<model id>`, at most 100 characters. The runner gives OpenCode the provider's URL and key for that turn only. A turn whose provider the runner lacks is not started. (2026-11-17-local-model-providers; Willem 2026-11-17, answer 22)
- The poll reports `model_providers` by name: `openrouter` when the project's key is set, plus each provider of the runner. The app never learns URLs or keys. (2026-11-17-local-model-providers)
- The poll reports each ready client's models (not OpenCode's) as its CLI lists them for its credential or login, its default first, plus Anthropic's list for a Claude Code API key and Google's `generateContent` models for a Gemini API key; and each provider's, `openrouter` first for a project with its key. Each list is fetched at start, after each detection and every 10 minutes in the background, each project asking its own clients, keeps its last good fetch when one fails, and goes with `models_age`, the seconds since that fetch; at most 500 ids the app accepts. (2026-11-24-model-lists; 2026-11-17-provider-models; CLR-218)
- A client's list comes from its live CLI in a short container of the default image with its state volume and turn environment, on Docker's default network, without a turn: Claude Code's `initialize` answer (each alias as its full `resolvedModel`), Codex app-server's `model/list` (hidden ones left out), `gemini models list`; stopped after its answer or 60 seconds. A Codex API key has the CLI's list only. A provider is asked `GET <base URL>/models` with its key as a bearer, `host.docker.internal` at `127.0.0.1`, 5 seconds each, once for the runner; OpenRouter's public list of models that take tools, without a key, while some project has its key. A list never fetched well is not sent (a client) or empty without an age (a provider). Ids are at most 100 characters for a client, 150 for a provider, of `A-Z a-z 0-9 . _ : / -`. (2026-11-17-provider-models; 2026-11-24-model-lists)
- A provider is marked free or not by whoever adds it (`add-provider --free`, `set-provider NAME --free=true|false`; not free by default). The poll reports the free ones as `free_providers`, at most 50, never `openrouter`, only names also in `model_providers`, left out when none is; the app prices their models at $0. (app decision 2026-11-19-free-model-providers; CLR-214)
- A provider may have `max_agents` (0 or none: no limit; at most 100; `add-provider`/`set-provider --max-agents N`): the most agent turns on it at once over every project, counted once for the process and across a reload. A turn is on it when its OpenCode agent's model names it; OpenRouter and the other clients' own providers have no limit. A `run` or `resolve` turn past the limit waits inside its step, logged once, keeping its slot and memory; a check, a publish and the time between steps hold no place; the poll's stop ends a waiting turn as `stopped`. (2026-11-25-provider-agent-limit)
- Such a provider also has `max_agents + lookahead` places for runs in play (`--lookahead N`, 0 to 100, default 0, refused without `max_agents`). A run is in play from the job taken with that `provider`, or its first turn on it, until it ends; a run that goes is never refused. Every poll that offers a slot reserves each limited provider's free places and sends them as `provider_places` (left out when none is limited); a place is in one poll at a time, and what the answer did not use goes back. A run leaving play wakes every project's loop at once; a place given back unused wakes none. A poll reporting 0 places logs once. (2026-11-26-provider-places; app decision 2026-11-25-provider-places)

## CLI, service and configuration

- `key list`, `key set` and `key delete` manage a project's secrets; `key set` reads from stdin, hidden on a terminal, and also takes `provider:NAME`. Each change reloads a running runner. (2026-11-10-model-keys; 2026-11-16-x-term; Willem 2026-11-17, extras)
- `add-provider`, `set-provider`, `list-providers` and `remove-provider` manage the runner's providers. (2026-11-17-local-model-providers; CLR-214)
- A command that changes the config or the secrets makes its change, reloads a running runner and returns at once, naming the issues that still run on the old config; `status` shows such a project until its loop has ended. Only `remove` and `rename` wait, for their own project's runs, before they remove its Docker volumes, and `update` drains the whole runner and restarts it. While one waits, `s` then `y` stops the runner at once, after which the service starts again; a Ctrl-C keeps the change. (2026-11-18-drain-before-reload point 3; 2026-11-24-rolling-reload)
- `remove` deletes a project's secrets, Docker objects and notes, unless another project shares its ID. (2026-11-11-audit-fixes)
- The service is user level everywhere: a LaunchAgent, a systemd user unit, a Windows logon task from XML via `schtasks /create /xml`. (2026-11-05-runner-rewrite-details; 2026-11-07-kardianos-service)
- The service restarts only on failure, so `cinderline stop` stops it until the next login; macOS does not restart a crash. (2026-11-07-service-restart)
- `config.json` holds no secrets; providers are in its top-level `providers` list. (2026-11-17-local-model-providers)
- The daemon serves the web page itself (`internal/web`), on `127.0.0.1` only, with no LAN or remote option: `web` (`"on"`, `"off"`, absent for the default, off for now) and `web_port` (1024 to 65535, default 7420), runner-wide. `cinderline web` prints the URL with the token and opens it in the browser (`--no-open`: print only); `web on|off`, `web port N` and `web --new-token` change it, and a running daemon takes the change at once. A taken port logs once at Error and the daemon runs on without the page. (2026-11-26-local-web-page)
- The page's parts: Overview, Runs (each opens its run), Projects (one page each, with add, rename and remove), Providers, Settings, and Log (the runner log, followed). It does everything the CLI does except `login`, `uninstall`, `service` and `run`, for which it shows the command to type. Removing or renaming a project needs its key typed; rotating the CA, stop, drain and update a plain confirmation. (2026-11-26-local-web-page)
- The page's look: a top bar, clear status colours, calm and mostly unboxed, "does anything need me?" first and the live run second, one column in the same order on every page, nothing that moves on its own. Light and dark follow the system until the top bar's switch is used, kept in that browser only. English only; current Chrome, Firefox, Safari and Edge; usable by keyboard and in a phone-width window. (2026-11-26-local-web-page; [2026-11-27-web-look](2026-11-27-web-look.md))
- `cinderline transcripts [--project KEY] [DAYS|clear]` and `cinderline transcripts --max-size SIZE` show and set `transcript_days` and `transcript_max_size`. (2026-11-26-local-web-page)

## Logging and errors

- Logging is `log/slog`, one structured line per event, tagged with project and issue. (AGENTS.md)
- The daemon's log rotates at 10 MB keeping 3; `cinderline logs` prints the tail and follows; `/logs` sends the last 100 lines. The socket folder is 0700, and a held socket is detected by dialing. (2026-11-05-reload-config; 2026-11-05-runner-rewrite-details)
- An agent turn's output, and a check's, goes to its transcript, not the runner log (2026-11-26-local-web-page). The output of a container run without a transcript is logged at Debug one line at a time, cleaned to printable text (a carriage return starts the line over) and redacted again after cleaning: `run -v` prints it as `time ISSUE │ line` with only its colour codes kept, and only on a terminal; the log file keeps the plain text. (2026-11-18-verbose-agent-output)
- Errors reach the app only in the poll's report and in `next`; the runner posts no comments. (2026-11-16-runner-protocol-v2)

## Testing and CI

- An issue is done only when `gofmt -l .` prints nothing and `go vet`, `staticcheck`, `go test -race ./...` and `govulncheck ./...` pass. (AGENTS.md)
