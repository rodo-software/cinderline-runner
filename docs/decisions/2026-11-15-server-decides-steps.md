# The app decides each step of a run and writes its prompt

- **Status:** Accepted
- **Date:** 2026-11-15 (the decision), 2026-11-16 (the design)
- **Source:** Willem chose option 2 on CSR-175 on 2026-11-15: move the "what next" policy and the prompt texts from the runner to the app. The CSR-177 issue text fixed points 2 to 4 and 10. Claude proposed the rest on CSR-177. Point 8 is Willem's answer on CSR-177 (option A, 2026-11-16).

## Decision

1. **`POST /runs/{ref}/next`** (`nextStep` in `docs/runner-api/openapi.yaml`, API version 1.1.0). The runner calls it at every step boundary of a run: before the first step, after each agent turn, each check and each base merge that conflicts. The app answers with the next step, and the runner does it. `ref` is the run's top-level issue. These move to the app:
   - **Policy:** `Attempts`, `Rounds`, `runSubIssues`, `subIssuesToRun`, `checkBudget` and `pendingCost`, the resume choices in `hookRun`, who resolves a merge conflict, and the check loop's fix count and verdicts (decision 2026-11-16-check-step).
   - **Prompt texts:** `CodingPrompt`, `GenericPrompt`, `LinkedSection`, `teamSection`, `AttachmentsSection`, `RoundPrompt`, `WorkerPrompt`, `ContinuePrompt`, `CommentsPrompt`, `ResumePrompt`, `FollowUpPrompt`, `FixPrompt`, `MergePrompt`, and the comment texts tied to those choices (`UnreadComments`, `GenericReport`, the budget, failure and check verdicts).

   The runner keeps the mechanics: containers, git (commits, base merges, verifying a resolved merge, pushes), the forge (pull requests, the merge wait, `merge_status` from the forge), the client adapters, tokens, sessions, paused and kept notes, the outbox, the failsafes of CSR-159 and their halt note, and the finish report built from the forge's answer.
2. **Stateless (0091).** The app keeps no run or step table. It derives the step from the issue, its sub-issues, comments and usage, and the request's facts. The attempt count, the fix count, the round's sub-issues and the comment cursor travel in an opaque `state` string, at most 8 KB. The app signs it, returns it, and the runner sends it back unchanged. The runner keeps it in memory only. A restart loses it, and the next run starts with `state: null`; the app then answers from issue state, as the runner does today after a restart (In progress sub-issues run again). The app treats a `state` it cannot verify as null.
3. **Closed set of steps.** `run`, `resolve`, `check`, `publish`, `finish`, `pause`, `fail` and `none`, each something the runner's open code already does. The table in `nextStep` says what each does. A step never carries a shell command, a path, a docker option, an environment variable or a URL. The check command stays the admin's `check_command` from `GET /project`. An attachment's `name` is one file name, which the runner refuses unless it is already safe (`fileName`). The runner's safety rules stay its own. A generic team's run never gets `check` or `publish` (CSR-75): the runner treats them there as unknown kinds. Tokens are created by the runner, with the kinds the app's token route allows. A kind the runner does not know stops the run with an error that names the runner's version. The runner commits and pushes first, and the issue goes to Blocked. The app sends a new kind only to runners whose `Cinderline-Runner-Version` knows it. Both sides ignore properties they do not know, and `reason` values are only logged. So a new step never does worse to an older runner than "stop with an error".
4. **Final prompt text from the app.** A `run` or `resolve` step holds the whole prompt, in the order of decision 2026-11-06-prompts. The request carries only what the runner alone knows: the branch, the base, the extra repositories it fetched (path, and URL without user info), and the folders of linked projects it fetched. The app names the attachments a step needs (`attachments`, null for a resumed turn). The runner downloads them with `downloadAttachment` into the emptied folder. So the app's prompt and the folder agree, and the runner no longer reads a sub-issue and its parent for them.
5. **Tracker writes.** Inside `next`, the app:
   - stores `last.usage`;
   - writes the progress line of the step it answers;
   - claims a To do sub-issue it runs;
   - after a sub-issue's last step, posts its report (with the check verdict) and moves it to Review;
   - posts the merge report after a `resolve`;
   - sets a trusted team's `merge_status` to `issue` for a conflict in Review.

   The runner pushes a sub-issue's commit before it calls, so 0122's "pushed after every sub-issue" holds. What ends a run stays with the runner, after its push, through the outbox: the final report, the move to Review or Blocked, and the budget stop's comment. So the push always comes before Blocked. The runner also keeps the "Started" progress line at the claim and its own lines about the environment, extra repositories and linked projects.
6. **Usage and budget.** Each turn's `UsageEntry` travels in `last.usage`, and the app stores it as `reportUsage` does. The app judges the budget on its stored usage, so `checkBudget`'s `GET /issues/{ref}`, `pendingCost` and the usage call at the run's end go. Over budget, the app answers `pause` with `block` and the "Budget reached" comment. The runner commits, pushes, moves the issue to Blocked and posts the comment. `last.id` lets the app store a retried call's usage once. `POST /runs/{ref}/usage` stays unchanged, used only by the outbox for usage that `next` could not deliver (point 8). This also settles CSR-93's batching: a normal run makes no usage request.
7. **Merge conflicts, in a run and in Review.** The runner merges the base in itself, as today: before the first step of continued work, at `publish`, and when it keeps Review branches current. A conflict goes to `next` as `last.step: merge`. The app decides who resolves it: `resolve` with the Merge Resolver, or with a solo team's agent in its session. Otherwise the conflict is pushed as it is (`publish` with `resolve_conflicts: false`), or nothing happens (`none`). The runner still verifies a resolution and undoes one that fails. In Review (`context: review`) the app answers `none` and sets `merge_status`, which is today's behaviour: no agent resolves Review conflicts (decision 2026-11-07-solo-team-resolves-merge-conflicts). Changing that is a later app decision plus a runner release that runs `resolve` in Review. The runner asks once per pair of branch and base commits, a cache it may lose, so a conflicted Review branch costs no request per poll.
8. **When `next` cannot be reached** (Willem: option A). The first call of a run failing means the run did not start: the issue goes back to To do, as for other start failures. A later call is retried after 2 and 8 seconds, as the outbox does. Then the runner ends the run as a `pause` with `block`: it commits and pushes the work, keeps the session in the paused note, and through the outbox moves the issue to Blocked with its own comment (Cinderline did not answer; the work is on the branch; move it to To do to continue). It sends the usage it holds with `reportUsage`. This replaces today's "publish with the unread note". Without the app the runner can no longer judge checks, comments or the budget, so it opens no pull request on its own. In Review a failed call is logged, and the next tick asks again.
9. **Later steps.** The check and fix runs of CSR-80 are already part of it (`check`, and a `run` that resumes the agent with the fix prompt). A gate or plan approval can be a `pause` with a new `reason`, which works with every runner, or a new kind under point 3.
10. **No fallback.** Cinderline is hosted only (EMBER-195), so the app ships `next` before the runner uses it. The runner has no code path for an app without it.

## What this changes in other decisions

- **2026-11-06-prompts:** the texts move to the app; the order (agent instructions, then rules, then the issue text last, as data) stays and binds the app. Point 2's team fields stay in the API; the runner no longer needs `description` and `price` itself.
- **App decision 2026-11-05-cost-per-issue-and-budget, point 5:** the app judges the budget. The runner still stops the run, after it commits and pushes.
- **2026-11-11-usage-and-budget:** point 2 (one usage call per run) and point 3 (the runner's budget check with the unreported cost) are replaced by point 6 above. Point 4 (preserve first, report second) stays.
- **2026-11-08-comment-cursor:** the cursor lives in `state`. The runner no longer reads comments around turns.
- **2026-11-16-check-step:** points 1 and 2 keep their behaviour, but the fix count, the fix prompt, the verdicts and the "no pull request after three fixes" end move to the app. The runner still runs the command.
- **2026-11-07-solo-team-resolves-merge-conflicts:** who resolves is the app's choice, with the same rules. The verification stays in the runner.

## Reason

The strategy (app decision 0104) is that the value sits in the backend. When Willem chose this, the runner was MIT and mirrored to public GitHub. Since 2026-11-16 it is FSL-1.1-ALv2 (decision 2026-11-16-fsl-licence). That forbids competing products, but not a person who points a self-downloaded runner at another tracker that implements this API. With the policy and the prompts in the app, the open runner only does what Cinderline tells it to. New policy (gates, plan approval, check variants) is built in the app without a public diff. Today's prompts and round engine stay in this repository's history.

Each `next` call replaces requests the runner already makes around a turn: the issue read for the status, the budget read, two comment reads, the progress lines and, per sub-issue, its claim, two issue reads, its comment and its move. So a run makes fewer requests than today (capacity estimate on CSR-175). A closed set of steps keeps the runner, which holds the user's credentials, inspectable: the app chooses among things the open code does, and never sends something to execute. Point 8 favours a pushed branch and a Blocked issue over a pull request the runner can no longer judge.
