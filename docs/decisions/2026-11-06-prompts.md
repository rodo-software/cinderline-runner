# Prompts: the agent's instructions first, and the team fields in the API

- **Status:** Accepted
- **Date:** 2026-11-06
- **Source:** Decided by Willem on CSR-27 (option A to both questions).

## Decision

1. **Order.** Every prompt keeps legacy's order: the agent's own instructions (`Team.agents[].instructions`) first, then the runner's rules, then the issue or sub-issue text last, marked as data. This is how the coding, worker and Merge Resolver prompts read. The "instructions" that AGENTS.md calls untrusted data are Cinderline's shared instructions (`list_instructions`), which reach an agent only through MCP, never in a prompt. CSR-27's wording "instructions go last" is not followed.
2. **Team fields.** The runner API's `Team` gets `max_sub_issues`, and each agent gets `description` (string or null) and `price` (`{input, output}` in USD per million tokens, or null), so the orchestrator's "Your team" section is ported unchanged. A null price reads "price unknown", as in legacy. The client's label ("Claude Code", "OpenCode") is mapped in the runner from `client`, since the API sends only the value.

## Reason

1. The agent's instructions are its role and rules; marking them as data would defeat them, change every prompt's structure and be new wording, which the plan rules out ("the same texts").
2. The plan asks for the same texts; the section can't be filled without these fields. `docs/runner-api/openapi.yaml` changes, so the app repository must mirror it, serve the fields and update its route test.
